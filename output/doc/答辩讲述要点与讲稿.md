# 云平台故障注入工具答辩讲述要点与讲稿

## 一、答辩需要讲述的部分

### 1. 选题背景与问题来源

讲清楚为什么要做这个项目：云平台由底层虚拟化、Guest OS、分布式应用和管理控制面共同组成，层次多、耦合强。单点资源异常、网络异常、进程失效或控制链路问题，可能在不同层之间传播并放大。传统等待自然故障暴露问题的方式周期长、成本高，也难以覆盖极端场景，所以需要主动、可控地构造故障。

这一部分对应论文第 1 章，重点突出两个关键词：云平台健壮性测试、故障注入。

### 2. 研究目标与项目定位

说明本项目不是单一脚本，而是一套面向云平台的多层次故障注入工具。目标是覆盖 IaaS 层、Guest OS 层和典型分布式应用层，支持故障配置、任务下发、日志回收、状态观测和恢复清理。

这一部分要强调“工具平台化”：从零散注入器，整合成可配置、可调度、可观测、可恢复的实验平台。

### 3. 系统总体架构

介绍平台的分层结构：

1. 用户交互层：Web 控制台、命令行入口和配置文件。
2. 控制与调度层：FastAPI 后端、任务解析、参数校验、SSH 分发、恢复清理。
3. 故障注入执行层：KVM/内核注入器、VM 用户态注入器、Hadoop/CloudStack 场景注入器。
4. 被测环境层：ARM64 + KVM/QEMU 虚拟化环境、三节点虚拟机集群、Hadoop 和 CloudStack 场景。
5. 结果与数据层：命令输出、日志、节点状态、业务状态和恢复结果。

这一部分对应论文第 3 章和 `docs/system_architecture.md`，答辩时建议配一张总体架构图。

### 4. 核心实现一：IaaS/KVM 层故障注入

讲宿主机和虚拟化层的底层注入能力。项目通过 Linux 内核模块、Kprobes/Kretprobes 等方式，对 KVM 和内核关键路径进行干预，例如：

1. CPU 寄存器与执行流异常。
2. 缺页异常、TLB 刷新、内存映射异常。
3. VFS 读写链路阻断。
4. KVM 状态查询与热迁移路径干预。
5. KVM ioctl 权限拒绝或状态失真。

这一部分要突出：底层注入精度高，能够模拟崩溃、I/O 错误、状态不一致、迁移异常等较隐蔽的问题。

### 5. 核心实现二：Guest OS 层故障注入

讲虚拟机内部或宿主机用户态的注入能力。项目在 `vm_injection` 中实现了：

1. CPU 高负载注入。
2. 内存泄漏/内存耗尽注入。
3. 网络延迟、丢包、断连和隔离。
4. 进程崩溃、挂起和恢复。
5. 基于 ptrace 的进程内存篡改。
6. ARM64 寄存器故障注入。

这一部分要突出：相比内核层，Guest OS 层工具更轻量、更容易复现业务常见异常。

### 6. 核心实现三：Hadoop 与 CloudStack 场景化注入

讲为什么需要场景化：通用故障注入只能制造资源、网络、进程异常，但 Hadoop 和 CloudStack 的故障还要映射到具体业务语义。

Hadoop 侧可讲：

1. NameNode、DataNode、ResourceManager、NodeManager 进程崩溃/挂起/恢复。
2. 网络延迟、丢包、乱序、隔离、心跳超时。
3. CPU、内存、磁盘填充、I/O 限速。
4. HDFS 安全模式、YARN 节点不健康、Map/Reduce 任务崩溃。

CloudStack 侧可讲：

1. Management Server、Agent、MySQL 等组件故障。
2. API 延迟、Agent 断连。
3. SystemVM 崩溃、迁移失败。
4. 存储只读、存储填满、数据库锁等管理面异常。

这一部分要突出：平台不只是“让机器坏掉”，而是能让上层系统进入更接近真实云平台的异常状态。

### 7. 控制面与 Web 集成

讲 `web_controller` 的作用：前端提供中文控制台，后端基于 FastAPI 暴露接口，读取 `config.json` 中的节点、路径和权限配置，通过本地命令或 SSH 将任务下发到目标节点。

可重点介绍这些接口与流程：

1. `/api/config`：返回节点和动作配置。
2. `/api/action`：执行单次故障注入动作。
3. `/api/testcases`：列出功能测试场景。
4. `/api/functest`：执行带有前置检查、注入动作、结果验证和清理逻辑的功能测试。
5. `/api/health`：平台健康检查。

这一部分要突出：控制面把底层复杂命令封装起来，提升了实验效率、可复现性和安全性。

### 8. 实验设计与验证方法

讲实验不是只看“能不能运行”，而是从四类指标评价：

1. 故障触发类指标：注入器是否准确作用到目标对象。
2. 系统行为类指标：CPU、内存、网络、进程、业务状态是否出现预期变化。
3. 恢复与容错类指标：故障结束后系统能否恢复到稳定状态。
4. 平台有效性指标：任务是否能统一调度、日志是否完整、恢复是否闭环、实验是否可重复。

实验可分为单层故障注入和跨层级联故障注入两类。

### 9. 实验结果与结论

总结实验发现：

1. 底层 KVM/宿主机故障容易引发崩溃、I/O 错误、状态失真等问题。
2. Guest OS 层故障更常表现为性能下降、节点响应迟缓、进程假死或资源耗尽。
3. Hadoop/CloudStack 业务层故障会进一步体现为任务重调度、节点失联、API 超时、控制面恢复延迟等现象。
4. 跨层级联故障不是简单叠加，而会放大系统对故障来源的判断难度。

这一部分要强调论文价值：平台能够揭示云平台中跨层传播、状态失真和恢复阻塞等传统单层测试难以发现的问题。

### 10. 创新点、不足与展望

创新点建议讲四点：

1. 面向 ARM64 与 KVM 环境，适配较新的虚拟化实验场景。
2. 构建覆盖 IaaS、Guest OS、分布式应用层的多层次故障注入体系。
3. 针对 Hadoop 和 CloudStack 实现带业务语义的场景化注入。
4. 通过 Web 控制面实现任务配置、调度、观测和恢复的统一封装。

不足与展望建议讲三点：

1. 当前结果分析仍以日志和现象归纳为主，后续可增加自动指标统计。
2. 前端可视化仍偏原型，后续可加入拓扑图、历史实验管理和模板复用。
3. 实验规模较小，后续可扩展到更多节点、更多云原生组件和 CI 自动化测试流程。

## 二、答辩讲稿

各位老师好，我的论文题目是《云平台故障注入工具》。我本次答辩主要从选题背景、研究目标、系统架构、关键实现、实验验证以及总结展望几个方面进行汇报。

首先介绍一下选题背景。随着云计算平台规模不断扩大，云平台已经不再是单一服务器或单一应用，而是由底层硬件、虚拟化层、客户机操作系统、分布式应用以及管理控制面共同组成的复杂系统。在这样的系统中，CPU、内存、网络、存储、进程以及控制链路中的任意一类异常，都可能在多层架构中传播并放大，最终影响平台的可用性和业务连续性。

传统测试方式往往依赖自然故障暴露问题，测试周期长、成本高，而且难以覆盖极端和隐蔽场景。因此，我的课题希望通过故障注入技术，在可控实验环境中主动模拟云平台运行过程中可能出现的典型异常，观察系统的检测、隔离、恢复和容错能力，从而为云平台健壮性测试提供工具支撑。

本项目的研究目标，是设计并实现一套面向云平台多层架构的故障注入工具。它不是单一的故障脚本，而是覆盖 IaaS 层、Guest OS 层和典型分布式应用层的一套工具体系。平台需要能够支持多种故障类型的主动注入，同时具备任务配置、统一调度、日志回收、状态监控和恢复清理能力，使故障实验能够重复执行、可观察、可分析。

接下来介绍系统总体架构。整个项目采用控制面和执行面分离的思路。上层是用户交互层，主要包括 Web 控制台、命令行入口和配置文件。中间是控制与调度层，由 FastAPI 后端实现，负责解析用户输入、校验参数、生成任务、通过本地命令或 SSH 分发到目标节点，并在实验结束后执行恢复清理。下层是故障注入执行层，包含三类注入器：面向 KVM 和宿主机内核的底层注入器、面向 Guest OS 的用户态注入器，以及面向 Hadoop 和 CloudStack 的场景化注入器。最底层是被测环境，包括 ARM64 + KVM/QEMU 虚拟化环境、三节点虚拟机集群，以及其上运行的 Hadoop 和 CloudStack 测试场景。

在总体设计中，我重点解决了三个问题。第一，不同层次的故障如何统一描述。平台将故障抽象为故障对象、注入方式、参数集合、预期影响和恢复方式。第二，多节点任务如何统一调度。控制面根据目标节点、故障类型和实验时序生成具体命令，再通过 SSH 或本地执行器下发。第三，实验过程如何可观测和可恢复。平台会回收命令输出、节点状态和关键日志，并为网络、资源、进程等故障提供相应清理逻辑。

下面介绍第一类核心实现，也就是 IaaS 和 KVM 层故障注入。这一部分主要位于 `kvm_injection` 目录中，采用 Linux 内核模块和 Kprobes/Kretprobes 技术，在宿主机侧对 KVM 和内核关键函数进行动态追踪与拦截。比如，在 CPU 相关模块中，可以在进程创建或 vCPU 相关路径上修改寄存器或执行流；在内存相关模块中，可以拦截缺页异常处理、TLB 刷新和 KVM 内存区域映射；在文件系统相关模块中，可以拦截 VFS 读写函数并返回 I/O 错误、空间不足或只读错误；在状态查询和迁移相关模块中，可以对 KVM 状态接口和脏页日志获取过程进行干预。

这一层的特点是注入位置更底层，能够模拟一些普通应用层工具难以构造的故障，例如虚拟机内存映射失败、磁盘 I/O 错误、虚拟机状态失真以及热迁移过程中的脏页信息异常。这类故障对于验证云平台底层虚拟化链路和控制面监控机制非常重要。

第二类核心实现是 Guest OS 层故障注入，主要位于 `vm_injection` 目录。这个层次的工具更多使用 Linux 用户态接口实现，例如 ptrace、tc、iptables 和 POSIX 信号。具体实现包括 CPU 高负载注入、内存泄漏和内存耗尽注入、网络延迟和丢包、网络隔离、进程崩溃、进程挂起与恢复，以及进程内存和寄存器篡改。

与内核级注入相比，Guest OS 层工具更加轻量，适合快速模拟业务系统中常见的资源异常和进程异常。例如，CPU 注入器可以通过多线程密集计算制造高负载；内存泄漏注入器可以持续申请内存模拟 OOM 压力；网络注入器可以通过 tc 和 iptables 构造延迟、丢包和隔离；进程注入器则可以通过 SIGKILL、SIGSTOP 和 SIGCONT 模拟崩溃、假死和恢复过程。

第三类核心实现是 Hadoop 和 CloudStack 的场景化故障注入。之所以需要这一层，是因为云平台故障不仅仅是底层资源异常，还会体现为业务语义上的异常。例如 Hadoop 中的 NameNode、DataNode、ResourceManager 和 NodeManager 都有特定的容错机制；CloudStack 中的 Management Server、Agent、SystemVM、API 链路、数据库和存储也有自己的管理逻辑。

在 Hadoop 场景中，项目支持进程崩溃和挂起、网络延迟、丢包、乱序、隔离、心跳超时、CPU 压力、内存压力、磁盘填充、I/O 限速、HDFS 安全模式、YARN 节点不健康，以及 MapReduce 任务崩溃等故障。通过这些故障，可以观察 Hadoop 主节点是否能感知工作节点异常、任务是否会重调度、HDFS 是否进入安全模式，以及节点恢复后能否重新加入集群。

在 CloudStack 场景中，项目支持 Management Server 和 Agent 的崩溃、挂起和恢复，API 延迟，Agent 断连，系统虚拟机故障，虚拟机迁移失败，存储只读、存储填满以及数据库锁等故障。通过这些场景，可以验证云管理平台在控制面链路异常、系统虚拟机异常和存储数据库异常下的可用性和恢复能力。

接下来介绍平台控制面的实现。项目中 `web_controller` 模块提供了一个中文 Web 控制台，后端使用 FastAPI 实现。配置文件 `config.json` 中保存节点信息、SSH 配置、各类注入器路径和 sudo 权限设置。前端页面调用后端接口，后端再根据具体动作构造命令并执行。

控制面中比较关键的接口包括 `/api/config`、`/api/action`、`/api/testcases`、`/api/functest` 和 `/api/health`。其中，`/api/action` 用于执行单次故障注入动作，`/api/functest` 则用于执行带有前置检查、注入动作、结果验证和清理逻辑的功能测试。这样做的好处是，测试人员不需要直接记忆每个节点的 IP、端口、脚本路径和清理命令，而是可以通过统一界面完成实验组织。

在实验设计方面，我将实验分为单层故障注入实验和跨层级联故障注入实验。评价指标主要有四类。第一类是故障触发类指标，用来判断注入器是否成功作用到目标对象，例如内核日志是否出现探针记录、进程状态是否变化、网络规则是否生效。第二类是系统行为类指标，用来观察 CPU、内存、网络、进程、节点和业务组件的变化。第三类是恢复与容错类指标，关注故障结束后系统能否回到稳定状态。第四类是平台有效性指标，关注平台自身是否具备统一调度、日志回收、恢复闭环和实验复现能力。

从单层实验结果看，宿主机和 KVM 层故障能够触发虚拟机崩溃、I/O 错误、状态查询异常等现象，说明底层注入器可以有效作用于虚拟化关键路径。Guest OS 层故障可以稳定制造 CPU 高负载、内存压力、网络劣化、节点隔离和进程状态变化，说明用户态注入器具有较好的轻量性和可复现性。Hadoop 和 CloudStack 场景实验表明，平台能够将底层或系统级故障映射到上层业务语义中，例如 Hadoop 节点失联、任务重调度、CloudStack API 超时和系统虚拟机恢复等。

在跨层级联实验中，我重点关注底层资源异常叠加上层网络异常，以及控制面异常叠加系统虚拟机异常这两类情况。实验分析表明，跨层故障并不是多个单层故障的简单相加，而是会出现更复杂的传播和放大。例如，底层资源异常会拉长节点响应时间，而网络隔离又会让主节点更难判断节点是性能退化还是已经失联；在 CloudStack 场景中，API 链路延迟叠加 SystemVM 异常后，恢复路径可能出现更明显的滞后。

综合来看，本文平台基本达到了预期目标。它能够覆盖宿主机虚拟化层、Guest OS 层以及 Hadoop、CloudStack 场景层的多类故障；能够通过统一控制面完成任务配置、动作下发、结果回收和恢复清理；也能够通过单层和跨层实验揭示云平台中资源异常、状态失真、控制误判和恢复阻塞等问题。

本项目的特色和创新点主要有四个方面。第一，面向 ARM64 与 KVM 环境展开故障注入研究，增强了对现代虚拟化实验环境的适配能力。第二，构建了覆盖 IaaS 层、Guest OS 层和典型分布式应用层的多层次故障注入体系。第三，针对 Hadoop 和 CloudStack 实现了带业务语义的场景化注入，使实验更接近真实云平台运行场景。第四，通过 Web 控制面将底层注入器整合为可配置、可调度、可观测、可恢复的平台化工具。

当然，当前工作仍然存在一些不足。首先，实验结果分析目前主要依赖日志对比和现象归纳，自动化指标统计和图表化展示还不够完善。其次，前端控制台仍偏向论文原型，在拓扑动态展示、历史实验管理和参数模板复用方面还有提升空间。再次，实验环境规模相对有限，主要用于验证平台机制本身，后续还可以扩展到更大规模集群和更多云原生组件。

后续工作可以从三个方向继续推进。第一，增强数据分析与可视化能力，引入时间序列指标、恢复时延统计和故障传播路径图。第二，扩展故障类型和目标环境，例如容器运行时、分布式存储、数据库复制和 Kubernetes 控制面故障。第三，提高自动化水平，加入实验模板库、故障组合推荐和自动恢复策略，使平台逐步从论文原型演进为可复用的云平台健壮性测试系统。

以上就是我的答辩汇报内容。请各位老师批评指正。

## 三、如果答辩时间较短，可压缩为 5 分钟版本

各位老师好，我的论文题目是《云平台故障注入工具》。本项目主要解决的问题是：云平台由虚拟化层、Guest OS、分布式应用和管理控制面组成，故障可能跨层传播并放大，传统测试方式难以及时发现这类问题。因此我设计并实现了一套面向云平台的多层次故障注入工具，用于主动模拟资源、网络、进程、虚拟化状态和管理链路异常。

系统总体上采用控制面和执行面分离的架构。控制面由 FastAPI 后端和 Web 前端组成，负责参数配置、任务调度、SSH 分发、日志回收和恢复清理；执行面包括三类注入器：面向 KVM 和宿主机内核的底层注入器，面向 Guest OS 的用户态注入器，以及面向 Hadoop 和 CloudStack 的场景化注入器。被测环境包括 ARM64 + KVM/QEMU 虚拟化环境、三节点虚拟机集群和典型分布式应用场景。

在关键实现方面，KVM 层通过内核模块和 Kprobes/Kretprobes 干预 CPU 寄存器、缺页异常、TLB 刷新、VFS 读写、KVM 状态查询和热迁移相关路径，用于模拟底层崩溃、I/O 错误和状态失真。Guest OS 层通过 ptrace、tc、iptables 和信号机制实现 CPU 压力、内存耗尽、网络延迟与隔离、进程崩溃与挂起等故障。Hadoop 和 CloudStack 层则进一步把通用故障映射到业务语义，例如 DataNode 崩溃、YARN 节点不健康、HDFS 安全模式、API 延迟、Agent 断连和 SystemVM 异常。

实验部分从故障触发、系统行为、恢复容错和平台有效性四个方面进行验证。单层实验表明，各类注入器能够稳定触发目标故障；跨层级联实验表明，底层资源异常和上层网络或控制面异常叠加后，会造成更复杂的状态误判和恢复延迟。最终说明平台能够支持多层次、多节点、可观测、可恢复的云平台故障注入实验。

本项目的创新点主要是：面向 ARM64 与 KVM 环境，构建了覆盖 IaaS、Guest OS 和分布式应用层的故障注入体系；针对 Hadoop 和 CloudStack 实现了场景化故障；并通过 Web 控制面将零散注入器整合为统一平台。后续工作会继续完善自动指标统计、可视化拓扑、历史实验管理，并扩展到容器和云原生控制面等更多场景。我的汇报到此结束，请各位老师批评指正。
